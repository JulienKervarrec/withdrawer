# Chapitre 8 -- Limites et perimetre de ce parcours

Ce parcours couvre l integralite de la logique metier de `withdrawer` : le point d entree `main.go`, les deux implementations du flux de retrait (`withdraw.go` pour L2OutputOracle, `fpwithdraw.go` pour les fault proofs), les utilitaires partages (`utils.go`) et le module de signature (`signer/`).

Sont volontairement laisses hors champ : le contenu du dossier `bindings/` (les interfaces Solidity generees automatiquement pour `AnchorStateRegistry`, qui ne sont que des enveloppes d appel sans logique propre a ce depot) ; le detail interne des fonctions de la bibliotheque `op-node` reutilisees telles quelles (`withdrawals.ProveWithdrawalParameters`, `withdrawals.FindLatestGame`, etc.), qui appartiennent au depot `ethereum-optimism/optimism` et non a `base/withdrawer` ; et deux limites explicitement signalees par des commentaires `TODO` dans le code source lui-meme -- l absence de generation automatique d une proposition de racine de sortie pour les retraits fault proofs, et l absence de gestion automatisee du cas ou une partie de contestation deja prouvee est invalidee apres coup (il faut alors relancer `withdrawer` manuellement pour qu il detecte l invalidation via `isDisputeGameInvalidated` et reprouve).

L objectif reste le meme que pour les parcours precedents de cette bibliotheque : comprendre precisement comment un outil en ligne de commande relativement court transforme la mecanique abstraite du pont op-stack -- MessagePasser, racines de sortie, parties de contestation, delai de contestation -- en une sequence de deux commandes que n importe qui peut executer pour recuperer ses fonds, sans pretendre couvrir l integralite de l ecosysteme op-stack.
